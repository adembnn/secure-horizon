## 1. Concurrents directs

### 1.1 TetraHelix Guard (HackQuest) - https://hackquest.io/projects/TetraHelix-Guard
- [P] Se décrit comme pare-feu "transaction-intent", non custodial, local-first, pour wallets : décode une transaction non signée EVM, compare à l'intention, signale approvals/transferts/swaps suspects. Extension navigateur multi-wallet, "provider-interception" privé, bridge authentifié. Wallet = signataire final.
- [P] Événement : Arbitrum Open House Singapore Online Buildathon (HackQuest), départ officiel 14 sept 2026. Chef d'équipe : Lucas Zoucha. Stade : pré-seed, auto-financé, cherche financements non dilutifs.
- [P] Pré-existant (non revendiqué comme nouveau) : coeur d'interception, bridge, inspection EVM. Nouveau pendant le buildathon : PolicyRegistry sur Arbitrum Sepolia (0x4e05...fbfaf, chaîne 421614), engagements de politique salés/versionnés, vérification runtime, UI démo, vérificateur de reçus. Tests : 22 privés + 21 publics.
- [P] IMPORTANT : "l'intention" = une POLITIQUE pré-configurée (hash engagé on-chain), pas une phrase déclarée à la volée. Le seul scénario de politique supporté dans le repo public est un auto-transfert natif de valeur zéro ; approvals, changement de destinataire, enveloppes malformées sont bloqués (ALLOW/BLOCK observé sur page de test locale avec Brave/MetaMask).
- [P] Ce qu'il ne fait pas (déclaré) : pas d'audit, pas mainnet, pas fonds réels, pas "authentification consensuelle de l'intention", pas escrow/recovery ; testé seulement sur une page locale contrôlée après bootstrap, pas sur sites hostiles ni tous wallets ; intégrité RPC/client et choix du registre = hypothèses de confiance ; écart entre vérification et signature (non atomique) ; sel de politique en mémoire navigateur, perdu au rechargement.
- [P] Code : repo public de démo https://github.com/11elevyngroup-png/guard-arbitrum-demo : 1 commit, 0 étoile/fork, pas de licence globale ("no additional blanket open-source license"), seul PolicyRegistry.sol est MIT. Extension, décodeur privé, bridge exclus (privés). Donc non réutilisable/auditable. Démo : vidéo YouTube ~3:55 + MVP web (pas un téléchargement d'extension).
- Non trouvé : usage d'un MetaMask Snap, simulation par fork (Anvil), saisie d'intention en langage naturel, Permit/Permit2, Avalanche. Le décodage est local (pas de simulation d'effet démontrée).
- Écart avec notre produit : politique figée vs intention déclarée par action ; interception côté extension (provider) vs Snap ; pas de simulation d'effet publiée.

### 1.2 IntentGuard (papier étudiant ITB)
- [P] Papier "Design and Evaluation of Transaction Intent Verification for Crypto Wallet Approval Phishing Mitigation Using EIP-712 Typed Data Signatures", Sarah Alwa Neguita Surbakti (NIM 18223023), STEI, Institut Teknologi Bandung, cours II4021 Kriptografi, S2 2025/2026. PDF : informatika.stei.itb.ac.id/~rinaldi.munir/Kriptografi-dan-Koding/2025-2026/ (fichier "Makalah2026").
- [P] Prototype web "IntentGuard Wallet" (React, Vite, ethers.js, MetaMask). L'utilisateur saisit un objet d'intention (wallet, spender, token, amount, chainId, nonce, deadline, verifyingContract), le signe en EIP-712, puis le système recouvre le signataire et vérifie que les données courantes correspondent, deadline non expirée, nonce non rejoué. Scénarios testés : falsification spender/token/montant/chainId, deadline expirée, rejeu de nonce : tous détectés (INVALID).
- [P] Ce qu'il ne fait PAS (déclaré) : n'envoie aucune vraie transaction, n'interagit pas avec un vrai ERC-20, ne décode ni ne simule aucune transaction réelle, nonce seulement en mémoire frontend. Il vérifie l'intégrité d'un objet signé par l'utilisateur lui-même, pas l'effet réel d'une transaction proposée par un dApp. Aucun lien code/démo public trouvé dans le PDF. Maturité : exercice de cours, aucune adoption.
- Écart : IntentGuard = cryptographie d'un message d'intention ; notre produit = comparaison intention vs effet simulé. Faible concurrence, utile seulement comme citation.

## 3. Limites techniques MetaMask Snaps

- onTransaction [P docs.metamask.io/snaps/reference/entry-points et features/transaction-insights] : permission `endowment:transaction-insight` ; reçoit `transaction` (brute non signée), `chainId` (CAIP-2, ex. eip155:43113), `transactionOrigin` (seulement si `allowTransactionOrigin: true`). Retour : `content` (ou `id` d'interface interactive via snap_createInterface) et `severity` optionnel, qui ne peut valoir que "critical".
- `severity: critical` sur onTransaction : [P] la doc indique "disponible uniquement dans Flask" (canary). Affiche une modale d'avertissement avant que l'utilisateur puisse confirmer. SIP-11 (brouillon, 2023) [P, lu via extrait de moteur ; page non récupérée, HTTP 503] décrit une modale avec case à cocher pour continuer. Donc : friction forte, mais l'utilisateur peut continuer ; la doc ne mentionne aucun blocage dur. Conclusion : un Snap ne peut qu'afficher/ajouter de la friction, pas bloquer [déduit, non affirmé explicitement par la doc].
- onSignature [P] : permission `endowment:signature-insight` ; reçoit `signature` (forme variable selon chaîne/méthode), `signatureMethod`, `signatureOrigin` (si `allowSignatureOrigin`). Méthodes EVM listées : eth_sign, personal_sign, eth_signTypedData, _v3, _v4. `severity` ne peut être que `SeverityLevel.Critical` ; le contenu s'affiche dans une modale APRÈS le clic sur Sign et, "à cause des limites actuelles de l'UI de signature", n'apparaît que si severity = critical. Statut Flask : la page d'accueil des Snaps range signature insights parmi les fonctions de la version stable [P] ; un résultat de moteur l'avait cité comme Flask-only (non confirmé). La doc ne dit pas que la sévérité côté signature est Flask-only. À tester sur Flask ET stable.
- Pas de simulation intégrée : le Snap doit appeler lui-même un service de simulation (permission réseau `endowment:network-access`). Un fork Anvil doit donc être joignable en HTTP depuis le Snap (hôte distant ; localhost à tester). Timeout/plafond d'exécution de onTransaction : non trouvé.
- Avalanche Fuji (chain ID 43113) : [P docs] le handler reçoit un chainId CAIP-2 ; la doc consultée ne liste pas de chaînes supportées et n'exclut pas les réseaux personnalisés. Que MetaMask appelle onTransaction pour un réseau personnalisé comme Fuji : non confirmé (à tester dans Flask).
- Distribution [P docs allowlisting/FAQ] : Flask = build développeur ; les Snaps allowlistés/audités apparaissent dans le Snaps Directory et s'installent sur la version stable ; sinon installation depuis Flask/npm. Étapes : formulaire, revue par l'équipe Snaps, 2 approbations, audit selon permissions (accès réseau = permission "protégée" revue manuellement). Pour un hackathon : démo Flask suffisante. Niveau de revue requis pour `transaction-insight` : non trouvé.

## 4. Simulation d'un permit / Permit2 / approve

- approve() (transaction on-chain) : une simulation peut décoder spender et montant ; les effets de solde sont nuls, donc une simulation de "changements de solde" ne montre rien de dangereux ; il faut lire la variation d'allowance. [déduit de la pratique ; pas de source primaire dédiée consultée]
- Permit / Permit2 (signature EIP-712 hors chaîne) : aucun effet on-chain à la signature ; la fraude intervient plus tard, quand l'attaquant soumet la signature [S : cryptonomist, SlowMist/Medium, SecureWorld, Decrypt ; résumés de moteur, articles non lus]. Les typed data sont difficiles à lire pour l'utilisateur ; Permit2 peut autoriser tout le solde ; une signature ouvre deux actions (Permit et TransferFrom) [S]. Une simulation "ce qui sortira du wallet" est donc vide à la signature ; il faut décoder le typed data (spender, token, montant, expiration, nonce) et projeter l'effet futur.
- Limite générale de la simulation : état sélectionné, pas le bloc final ni l'ordre ; la tx simulée peut différer de celle signée (Radiant Capital) [P EF blog]. presign-guard ne simule pas les signatures [P].
- Blockaid/Wallet Guard : traitement exact des typed data Permit2 : non trouvé.
- Conséquence produit : pour Permit/Permit2, le Snap doit s'appuyer sur onSignature + décodage viem du typed data, pas sur un fork Anvil.

## 5. Risques et angles pour le pitch
- Ne pas affirmer "premier" : presign-guard (intent en une phrase, agents) et TetraHelix (intent-firewall) existent.
- Différenciants possibles : saisie en mots simples orientée scénarios humains (payer quelqu'un, envoyer vers Coinbase, acheter une crypto, se connecter, "on m'a demandé"), dans MetaMask via Snap, avec simulation fork.
- Risque : sévérité critique = Flask seulement pour onTransaction ; l'intention doit parvenir au Snap (qui ne lit pas l'UI du dApp) via une page compagnon/snap_dialog/stockage : mécanisme à concevoir, non couvert par la recherche.
