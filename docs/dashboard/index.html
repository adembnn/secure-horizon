Comment Sentinelle est construite

Deux gardes indépendants du circuit d'approbation : un plafond gravé dans le coffre et une demande signée par le client. Autour, un surveillant qui ne peut que resserrer, un journal de preuves ancré sur Fuji, et un dossier DORA prêt à relire.

4 · Les trois contrats

GuardedVault
détient les fonds, non mettable à jour
  • deposit(amount)
  • tryWithdraw(request, clientSig) → refus par événement, pas de revert
  • tighten(params) : valeurs ≤ actuelles seulement
  • proposeLoosen / executeLoosen : 2 gardiens sur 3 + délai
ClientRegistry
qui a le droit de demander un retrait
  • enroll(client, key, guardianSigs) : 2 sur 3 + délai + quota par jour
  • isEnrolled, keyOf
EvidenceAnchor
la preuve, scellée sur Fuji
  • commitRules(hash) : avant les tests
  • anchor(root, kind) : racine du journal
  • commitMandate(hash) : plafonds signés par la direction

6 · Ce que les tests doivent prouver

  1. Quelle que soit la séquence, la sortie sur une fenêtre reste sous le plafond global.
  2. Par client et par jour, sous le plafond par client.
  3. tighten ne peut jamais augmenter un paramètre.
  4. Relâcher exige 2 gardiens sur 3 et le délai.
  5. Une demande signée ne sert qu'une fois.
  6. Aucun rôle ne retire sans demande valide.

Prouvés par des tests aléatoires (fuzzing) : c'est la « perte maximale démontrée ».
